# 模式 1 — 看清，再动手

目标不是「读完了」，是**能在不看代码的情况下把这块逻辑讲给同事听**，并且他知道该改哪一行。

## 勘察顺序

按这个顺序走，前一步的输出是后一步的输入。不要跳到最后一步直接看目标文件。

| # | 看什么 | 具体动作 |
| --- | --- | --- |
| 1 | 入口文档 | `README`、`CONTRIBUTING`、`docs/` 里跟构建和约定有关的页。找不到就说「没有文档」，别猜 |
| 2 | 技术栈 | 锁文件与清单：`package.json` / `pyproject.toml` / `go.mod` / `Cargo.toml` / `pom.xml` / `*.csproj`。注意**版本**，不是只有名字 |
| 3 | 怎么跑 | `Makefile`、`package.json` 的 `scripts`、`tox.ini`、`.github/workflows/*`。这里能拿到真实的测试命令和 lint 命令 |
| 4 | 入口 | `main.py` / `__main__.py` / `src/index.ts` / `cmd/*/main.go` / `src/main.rs`。搞清楚请求是怎么流到目标代码的 |
| 5 | 目标文件全文 | 不是搜关键词看片段，整文件读。上下文在行间 |
| 6 | 相邻的 2–3 个同类文件 | 同目录同角色（都是 service、都是 route、都是 widget）。这是**风格证据**，后面所有新代码都照它写 |
| 7 | 调用方与被调用方 | `grep` 目标函数的名字。上游是谁、传什么；下游依赖什么、抛什么 |
| 8 | 测试 | 找同类功能的测试文件，看它怎么搭数据、怎么断言、怎么 mock。**这就是你后面要写的测试的样子** |
| 9 | 配置 | 环境变量从哪读、有没有默认值、`config.py` 还是 `.env`。新增开关前先确认已有约定 |
| 10 | 数据形状 | 模型/schema/类型定义。字段的真实类型（`Decimal` 还是 `float`？时区带不带？） |
| 11 | 最近 10 条提交 | `git log --oneline -10`，再看 1–2 个完整 diff。**当前团队真正在用的写法在这里，不在文档里** |
| 12 | 失败面 | 这个功能出错时用户看到什么？有没有统一的错误处理中间件、日志、重试 |

工具：`python scripts/survey.py` 能一次给出 1–4、8、11 的大部分内容。

## 必须能回答的 12 个问题

答不上来的，就是还没读懂——回去看，别急着提问。

1. 跑测试的确切命令是什么？单跑一个测试文件的命令是什么？
2. 这个功能的上游入口是哪个路由/命令/事件？
3. 出错时异常往上抛还是就地处理？项目统一在哪一层兜底？
4. 日志怎么打？用 `print` 还是 logger？有没有 request id？
5. 新增一个函数，放在哪个文件、叫什么名字、`public` 还是 `private`？
6. 有没有依赖注入/工厂/单例的约定，新东西该挂在哪？
7. 数据访问是 ORM 还是裸 SQL？事务边界画在哪一层？
8. 返回给前端的数据结构在哪个 schema 定义？加字段要不要改类型声明？
9. 有没有 feature flag / 灰度机制？新逻辑要不要包起来？
10. 数据库改动怎么上？迁移脚本放哪、命名什么格式？
11. 这个函数还有谁在调用？改了会不会影响别的入口？
12. 现有测试里，跟这块最像的是哪一个？

## 复述模板

四段，缺一段都算没过门。写进回复里，不要只在脑子里过。

```
【需求】
一句话：<动词 + 对象 + 条件>。不许用「优化」「完善」「支持一下」这种词。
现状：<现在是怎么做的，带 file:line>
差距：<具体差在哪，不是「不够好」>

【我打算改】
- <文件:函数> 做 <什么>，预计 <N> 行
- 不改：<明确列出这次不碰的东西，尤其是不碰的相邻逻辑>

【关键假设】
| 假设 | 依据 | 不成立会怎样 |

【待确认】
<最多 3 个，按重要性排；没有就写「无」>
```

「现状」那一行最能暴露读没读懂。写不出 `file:line` 就是没读。

## 假设清单怎么写

假设不是免责声明，是**风险登记**。

| 假设 | 依据 | 不成立会怎样 |
| --- | --- | --- |
| `order.amount` 已经是 `Decimal` | `models.py:34` 字段类型 `NUMERIC(12,2)`，SQLAlchemy 映射为 `Decimal` | 如果上游某处塞了 float，累加会丢精度，对账差 1 分 |
| 这个接口只被管理后台调用 | `grep` 到 2 处调用，都在 `admin/` 下 | 若有外部调用方，加必填参数就是破坏性变更 |

每行都要有「依据」。没有依据的假设要降级成问题去问——或者标成「未知风险」并说明怎么验证。

## 提问过滤器

这是本模式最重要的一条。**AI 最常见的坏习惯是把该自己查的东西丢给用户。**

一个问题必须同时满足三条才问：

1. **代码库里查不到**（不是懒得查，是读完了确实没有）
2. **答案会改变方案**（不是「知道了更好」，是「不知道就选不了」）
3. **不是偏好问题**（偏好应该按现有代码的多数派决定，不该问）

| 别问 | 该问 |
| --- | --- |
| 「你希望用什么测试框架？」 | 已经装了 pytest，`pyproject.toml:28` |
| 「数据库是什么？」 | `docker-compose.yml` 里写着 postgres:16 |
| 「要不要加日志？」 | 相邻文件都在用 `logger.info`，跟着写 |
| 「这个函数能不能改签名？」 | `grep` 到 3 个调用方，其中一个是外部 SDK 的回调——**这个要问** |
| 「边界怎么处理？」 | 现有代码对同类输入是抛 `ValueError`，跟着抛 |
| 「要不要保留旧接口？」 | 旧接口有 2 个调用方在别的仓库，改不了——**这个要问** |
| 「用什么命名风格？」 | 同目录全是 `snake_case`，跟着写 |
| 「生产环境的表有没有这个索引？」 | 迁移脚本是唯一真相源，本地看不到线上实际状态——**这个要问** |

一句话判据：**能通过读文件、搜索、跑命令回答的，一律不许问。** 跑不了命令（比如线上状态、业务规则、合规要求）才是真问题。

## 反模式

- **只看了目录树就开始复述**。目录树告诉你有什么文件，不告诉你它们怎么协作。
- **复述需求时用同义词改写用户的话**。那是复读，不是理解。理解体现在能说出「现在这段代码在 `x.py:88` 处做了 A，你要的 B 需要把 A 换成 C」。
- **列了 8 个假设，每个都不痛不痒**。「假设用户会用合法输入」这种不叫假设，叫废话。假设要能指向具体的失败后果。
- **一次问 6 个问题**。超过 3 个，说明前 3 个里有能自己查的。砍到 3 个以内，按影响排序。
- **方案写得像设计文档**。最小方案的篇幅应该和改动量成正比——改 20 行不需要 200 字的架构说明。
