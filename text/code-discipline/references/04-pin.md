# 模式 4 — 先固定行为，再重构

重构的定义是「**不改外部行为，只改内部结构**」。所以重构的第一个动作不是改代码，是**用测试把「外部行为」这个词变成可执行的东西**。

固定测试记录的是**事实**，不是**意图**。它断言「现在是这样」，不管这样对不对。

## 硬门

新写的一组测试，**在完全未修改的原代码上必须全绿**。

- 全绿 → 这组测试就是安全网，可以开始重构。
- 有红 → 你发现了 bug。**不要在这个阶段修**，记下来，切模式 3 单独处理，或者向用户报告后决定优先级。

这一条把「重构」和「修 bug」彻底分开。混在一起做，出问题时你无法判断是重构改坏了还是 bug 本来就在。

## 12 类行为矩阵

按这个表逐项过，过完就是一套能兜住重构的网。

| # | 类别 | 要固定什么 | 例子 |
| --- | --- | --- | --- |
| 1 | 正常路径 | 典型输入 → 输出 | `split([1,2,3], 2) == [[1,2],[3]]` |
| 2 | 空输入 | `None` / `""` / `[]` / `{}` 各自的返回**或**异常 | `split([], 2) == []`；`split(None, 2)` 抛 `TypeError` |
| 3 | 单元素 | 只有 1 个元素 | `split([1], 5) == [[1]]` |
| 4 | 边界值 | `0`、负数、类型极值、超长 | `split([1,2], 0)` 现在**死循环**——这就是要固定的现状 |
| 5 | 重复调用 | 连调两次结果是否一致；有没有累积状态 | 第二次调用返回相同的值，还是追加了？ |
| 6 | 顺序依赖 | 换个顺序结果变不变 | 字典遍历顺序、并发下的输出顺序 |
| 7 | 错误路径 | 抛什么异常、消息文本、是否被包装 | `pytest.raises(ValueError, match="size must be")` |
| 8 | 副作用 | 写了什么、写了几次、什么顺序 | 调用一次 `db.commit()` 还是 N 次 |
| 9 | 返回值形状 | 字段名、类型、嵌套层次、`None` vs `[]` | 返回 `{"items": [...]}`，不是裸 list |
| 10 | 编码 | 中文、emoji、组合字符、超长字符串 | 名字带 emoji 时长度截断会不会切断字符 |
| 11 | 时间 | 时区、DST、只有日期没有时间 | 返回的是 `UTC` 还是本地时间？naive 还是 aware？ |
| 12 | 精度 | 浮点误差、舍入方式、货币 | `0.1 + 0.2` 现在到底返回多少 |

**第 4、10、11、12 类是最容易漏、也最容易在重构后悄悄变的。** 优先写它们。

## 怪行为怎么固定

原代码里那些「看着就不对但一直这样跑」的地方，必须**原样固定**，并标注原因。否则重构时你会「顺手修正」它，然后下游某个依赖这个怪行为的地方崩了。

```python
def test_split_with_zero_size_hangs():
    """现状如此：size=0 会死循环。重构时必须保持不变，
    或先单独确认没有调用方传 0（grep 到 3 处调用，都传的是常量 100）。"""
    # 用一个超时装饰器或子进程来固定「会挂住」这个事实
    ...

def test_split_negative_size_returns_empty_not_raises():
    """现状如此：负数返回空列表，不抛异常。看上去是 bug，
    但 api/batch.py:61 依赖这个行为做短路，不要顺手改成抛错。"""
    assert split([1, 2], -1) == []
```

要点三条：

1. **测试名说事实**，不是「应该怎样」。`test_negative_size_returns_empty` 好过 `test_negative_size_should_raise`。
2. **docstring 写清「为什么保留」**——谁依赖它、有没有替代方案。
3. **能证明依赖关系的，把依赖方也写进 docstring**（`api/batch.py:61`）。这样下一个人才不会删掉。

## 重构后测试一行不改

除了**搭建方式**（fixture、构造参数），断言部分一个字都不许动。

如果重构后发现测试必须改才能过，只有两种可能：

| 情况 | 说明 | 处理 |
| --- | --- | --- |
| 测试耦合了实现细节 | 它断言了私有方法、内部调用次数、内部数据结构 | 测试写得太白盒。改成断言公开行为，**这个改动本身要报告** |
| 重构真的改了行为 | 你改的不叫重构 | 停下来。要么回退这次改动，要么承认这是行为变更并走完整流程 |

第二类是隐蔽的破坏：把一个「重构」做成了「行为微调」，测试拦住你的时候，改测试是最顺手的动作，也是错的。

## 覆盖率不是目标

目标只有一个：**被重构的那部分，所有分支都有断言**。

- 别去追整体覆盖率数字。涨了不代表网结实，可能只是测了一堆 getter。
- 重构前的自检：把要重构的函数里每个 `if` / `except` / 提前 `return` 列出来，每一条都要有一个测试能走到。
- 拿不准的地方：**在这个分支上改一行 `raise RuntimeError("hit")`，跑测试**。没有测试变红，说明这个分支没被覆盖。

最后这个技巧比覆盖率报告准得多。

## 汇报格式

```
固定完成：8 个测试，原代码上 8 passed（412 total passed）
覆盖：正常 / 空 / 单元素 / size=0 死循环 / 负数返回空 / 中文截断 / 时区 / 精度
发现 2 个现状怪行为（已固定，未修改）：
  - size=0 死循环（无调用方传 0，grep 结果 3 处）
  - 负数返回 [] 而非抛错（api/batch.py:61 依赖它）
未覆盖：并发场景（当前实现有全局锁，无法从外部触发）
```

「未覆盖」那一行不能省。**说清网哪里还有洞，比声称网是密的更有用。**

## 反模式

- **补测试时顺手把「明显不对」的地方改掉**。你已经越界到修 bug 了，而且是没走模式 3 的那种。
- **只测 happy path，理由是「重构不会影响错误路径」**。错误路径恰恰是最容易被重构改坏的（异常被包装、被换成 else 分支）。
- **用 mock 把被测函数的外部依赖全挡掉**，然后断言 mock 调用次数。重构会把调用次数改掉，这种测试必然要改。
- **测试名写成 `test_refactor_safety_1`**。三个月后没人知道它固定的是什么。
