# 模式 6 — 提交审查

范围：**最后一次提交**。只查三类：安全、性能、逻辑。**风格问题一条都不提。**

## 取范围

```bash
git log -1 --stat                      # 先看改了什么、改了多大
git show HEAD --format=fuller          # 完整 diff + 提交信息
git diff HEAD~1 -- path/to/file        # 单个文件的改动
```

同时看**没改但强相关**的文件：改了 `service` 就要读它的 `repo` 和 `model`。问题经常在接缝处，不在 diff 里。

## 三张检查表

不是全查一遍，是**按 diff 触发**：diff 里出现 `execute`，查 SQL 注入；出现 `for` 包 `await`，查 N+1；出现 `commit`，查事务边界。下面按「diff 里出现什么」索引。

### 安全

| diff 里出现 | 查什么 |
| --- | --- |
| `execute` / `query` / 字符串拼 SQL | 参数化了吗？`f"... {x}"` `%` `.format` 全是红旗。`IN` 子句尤其容易拼 |
| `subprocess` / `os.system` / `exec` | `shell=True`？参数来自用户？ |
| `open()` / `Path()` / `send_file` | `../` 能不能穿出去？绝对路径拼接了吗？ |
| `pickle` / `yaml.load` / `eval` | 数据来自不可信来源？`yaml.safe_load` 才对 |
| `render_template_string` / 模板拼接 | 用户输入进模板字符串 = SSTI |
| `requests.get(url)` / `httpx` | URL 来自用户？内网地址可达？= SSRF |
| `find_by_id(id)` 后直接返回 | 查了归属吗？`where user_id = current_user` 有没有 = IDOR 越权 |
| `**request.json` / `update(**data)` | 批量赋值，`is_admin` 能被客户端写进去吗？ |
| 常量字符串像密钥 / token / 密码 | 硬编码凭据。测试密钥也算 |
| `logger.info(..., user)` / 打印整个对象 | 密码、token、身份证、卡号进日志了吗？ |
| `md5` / `sha1` / `hashlib` 做密码 | 必须用 bcrypt/argon2/scrypt + salt |
| `random.choices` / `random.randint` 生成 token | 必须是 `secrets` |
| `token == expected` | 时序攻击，应 `hmac.compare_digest` |
| 文件上传处理 | 白名单扩展名？大小上限？文件名是否被直接用作路径？ |
| `allow_origins=["*"]` | 同时 `allow_credentials=True` 就是漏洞 |
| JWT 解析 | `algorithms=["none"]`、不验签、不验 `exp`、不验 `iss` |
| `redirect(next)` | open redirect，`next` 要白名单 |
| 权限判断 | 只在前端隐藏按钮、后端没查？判断用的是角色名还是硬编码 id？ |
| 新增依赖 | 包名是否靠谱（typosquatting）、版本是否锁死 |
| 新增接口 | 有没有挂到鉴权中间件后面？内网路由组是不是漏了？ |

### 性能

| diff 里出现 | 查什么 |
| --- | --- |
| `for` 里查库 / 发 HTTP / 读文件 | N+1。50 条循环就是 50 次往返 |
| ORM 关系属性（`order.items`） | 惰性加载触发 N+1，需要 `selectinload` / `joinedload` |
| `LIKE '%x%'` / `func.lower(col)` | 索引用不上，全表扫 |
| `SELECT *` 在大表上 | 多余列传输，且加了列就自动变大 |
| 查询没有 `limit` | 无分页，数据涨了必然出事 |
| 缓存写入 | 失效策略？改了数据清缓存吗？key 的粒度对不对？ |
| 循环里的不变式计算（`len(x)`、正则 `compile`、配置读取） | 提到循环外 |
| `time.sleep` / 大文件同步读写 | 在请求路径上阻塞 |
| 新的全局 list/dict 累加 | 无界增长，内存泄漏 |
| `threading.Lock` 包住整个函数 | 锁粒度过大，吞吐归零 |
| 每次请求新建 `Client` / 连接 | 连接不复用 |
| 事务里调外部 API | 事务持有时间被网络延迟放大，锁等待堆积 |

### 逻辑

| diff 里出现 | 查什么 |
| --- | --- |
| `commit()` 在循环里 | 部分写入。失败时前面的已经落库 |
| `float` 参与金额 / 累加 | 精度丢失。金额用 `Decimal` 或整数分 |
| `<` vs `<=`、`range(n)` vs `range(n+1)` | off-by-one，尤其分页和批量切片 |
| `if x:` / `if not x:` | `0`、`""`、`[]` 都是假值。想判 `None` 就写 `is None` |
| `except: pass` / `except Exception` | 吞掉了什么？回滚失败也被吞？连接坏了还放回池？ |
| 状态字段赋值 | 有没有校验迁移合法性（`paid` 能不能直接到 `refunded`） |
| 创建类接口 | 幂等吗？重试会不会产生两条 |
| `datetime.now()` / `date.today()` | naive 时间，服务器 UTC 时用户看到差 8 小时 |
| `sorted()` / `set` / `dict` 遍历输出 | 顺序稳定吗？多键排序有没有 tie-breaker |
| 布尔参数默认值 | `enabled=True` 还是 `False`，和调用方预期一致吗 |
| 提前 `return` | 跳过了 `finally` 之外的清理？锁没释放？ |
| 文件/连接/游标 | 异常路径上也关闭了吗 |
| 条件短路 `a and b()` | `b()` 的副作用会不会在某些输入下不执行 |
| 404 vs 403 | 返回 404 藏存在性，还是 403 泄露了资源存在 |
| `is` 比较字符串/数字 | 小整数缓存和驻留字符串会让它「看起来能用」 |

## 每条发现的格式

四个字段，一个都不能少：

```
[严重度] 一句话标题
文件:行        app/api/orders.py:88
触发条件      GET /orders/batch?ids=1) UNION SELECT ... --
后果          任意 SQL 片段拼进查询，可读出 users 表
修法          占位符 + ANY(%s)，ids 先 int 校验并限长 100
```

**触发条件必须是可执行的**：具体的输入、具体的时序、具体的数据状态。写「如果用户输入恶意内容」等于没写。

| 严重度 | 判据 | 处理 |
| --- | --- | --- |
| **block** | 安全漏洞、数据错误、崩溃，且外部可触发 | 本 PR 必修 |
| **warn** | 逻辑错误或性能问题，触发条件常见 | 本 PR 必修或明确承诺时间 |
| **note** | 性能隐患、可维护性风险，触发不常见 | 可以另开 PR |

## 措辞禁令

| 不许写 | 改写成 |
| --- | --- |
| 「建议考虑加个索引」 | 「`orders.py:42` 在 500 万行上全表扫，p99 约 1.2s，建议加 `(user_id, created_at)` 索引」 |
| 「这里可能有并发问题」 | 「两个请求同时执行 `orders.py:120` 的读-改-写会丢更新，触发条件：同一订单 100ms 内两次提交」 |
| 「或许可以优化一下」 | 要么给出具体问题和数字，要么不提 |
| 「代码风格建议统一」 | 不提。这不是本次范围 |
| 「感觉不太对」 | 指出哪个值、在什么输入下、会错成什么 |

判据：**每一条都要能被对方拿去写测试。** 写不出触发条件的，说明你自己还没确认。

## 没发现问题也要给证据

空结果不是「没话说」，是「查过了，没有」。列出实际查了什么：

```
安全：SQL 全参数化（3 处 execute 已核）；无新增外部调用；鉴权中间件覆盖新路由；
      日志只打印 order_id 与数量
性能：新增查询有 (user_id, created_at) 索引；无循环内 IO；分页有 limit
逻辑：事务为单次 commit；金额用 Decimal；错误路径有 rollback
结论：三类未发现问题
```

这样别人才知道你是真看了，而不是敷衍。

## 常见漏查

审查最容易停在「diff 里的明显问题」，这几处最容易滑过去：

1. **错误路径**。正常人只看 happy path。异常分支里漏 rollback、漏释放、漏日志。
2. **没改的地方**。新代码调用了一个老函数，老函数本身有 bug——diff 里看不到。
3. **配置和迁移**。改了代码没加索引、加了字段没写迁移、改了默认值没同步 `.env.example`。
4. **权限**。新接口默认继承什么权限？如果路由组写错了，默认可能是公开的。
5. **日志与监控**。新代码出错时，日志里能不能定位到是哪一次请求？
6. **删除的代码**。diff 里 `-` 开头的行，删掉的东西还有人在用吗？

## 反模式

- **把审查做成风格检查**。命名、缩进、import 顺序、注释多少——一律不提。提了就会挤掉真正的问题。
- **列出 30 条「建议」**。审查的价值在于排序，不在于数量。超过 8 条基本等于没排优先级。
- **只报问题不给修法**。指出问题的成本很低，给出可执行修法才是审查。
- **对着 diff 逐行读**。要按「数据流」读：输入从哪进、经过谁、写到哪。问题在流上，不在行上。
- **说「这个我不确定」**。要么查清楚，要么明说「未验证，需作者确认 XX」。
