# 模式 3 — 先复现，再修

硬门只有一条：**在没改过任何代码的当前分支上，有一个测试失败了，而且失败信息指向用户描述的症状。**

不满足这一条，就还是在猜。

## 顺序

| 步 | 动作 | 判据 |
| --- | --- | --- |
| 1 | 用**最小输入**写一个测试，断言**症状**（不是断言内部实现） | 测试名能当 bug 标题用：`test_batch_create_returns_500_when_third_item_out_of_stock` |
| 2 | 跑它，**必须红** | 红的原因必须是断言失败，不是 ImportError / 环境缺依赖 / 找不到文件 |
| 3 | 把红的输出**原样存下来**（贴进汇报或写进 `out/repro.txt`） | 这是后面判断「修好了」的唯一基准 |
| 4 | 定位根因：从输入到错误的那条链，逐环排除 | 能指出具体 `file:line`，并解释**为什么**这里出错 |
| 5 | 改代码（可以多轮），每轮只改一处，跑同一个测试 | 变绿的那一次，就是根因所在的那一处 |
| 6 | 跑全量测试 | 没有新红 |
| 7 | **不许删测试**。它是永久回归测试 | 留在仓库里，命名指向症状 |

## 失败信号分级

看到红色不要高兴太早，先分清是哪种红：

| 信号 | 说明 | 处理 |
| --- | --- | --- |
| 断言失败，值是错的（`assert 500 == 200`） | 真复现 ✅ | 继续 |
| `AssertionError` 值是对的但类型不对（`'3' != 3`） | 大概率真复现，但要确认这是不是用户看到的症状 | 继续，但记录类型差异 |
| 抛出了用户没提到的异常（`KeyError`） | 可能是**另一个** bug，也可能是你的测试搭错了 | 先确认这条路径是不是用户真实走的路径 |
| `ImportError` / `ModuleNotFoundError` | 环境或写法问题，**不是复现** | 修测试，重来 |
| 超时 / 连不上数据库 | 环境问题 | 修测试环境，不要绕过 |
| 测试一跑就绿 | 没复现 ❌ | 见下面「跑绿了怎么办」 |

### 跑绿了怎么办

说明你的测试没打中。按顺序试：

1. **输入不够极端**：用户说「偶尔失败」，那就要并发或乱序，单线程跑不出来。
2. **前置状态不对**：bug 依赖「已有 2 条订单」这种状态，测试里数据库是空的。
3. **走了另一条分支**：mock 把真实路径挡住了，代码根本没执行到。
4. **环境差异**：本地 sqlite、线上 postgres；本地 UTC、线上 Asia/Shanghai；本地 Python 3.12、线上 3.9。
5. **它已经被修了**：`git log` 看看这个文件最近有没有人动过。如果确实修了，明说「bug 在当前 HEAD 上不复现」，并给出证据。

五条都试过还是绿——那就不是 bug，或者是环境/数据问题。**照实说，不要为了交差编一个根因。**

## 定位根因的手法

### 1. 二分注释

把可疑的一段注释掉/短路掉，看症状是否消失。消失了，问题就在这段里；没消失，继续往上游二分。

```python
# cur.execute(sql)          # 注释掉这行
return {"items": []}        # 直接返回空
# → 500 消失，说明异常来自 execute
```

### 2. 打点日志

在链路的关键节点打输入与输出。**打在边界，不要打在每一行**：

```python
logger.debug("batch ids raw=%r", raw)
logger.debug("batch ids parsed=%r", ids)
logger.debug("batch sql=%s", sql)
```

一次跑完就能看到哪一环的值不对。

### 3. 缩小输入

从 3 条降到 2 条、1 条、空。从 3 个字段降到 1 个。找到**最小触发条件**——最小触发条件本身就是根因的强线索。

### 4. git bisect

「昨天还好好的」用这个。`git bisect start`、标记 good/bad，几十步内能定位到某次提交。

### 5. 对比法

同一个函数在两个环境/两套数据下行为不同 → 差异就是根因候选。逐项对齐版本、时区、配置、数据。

## 四种假根因

| 假根因 | 为什么诱人 | 怎么排除 |
| --- | --- | --- |
| **异常栈顶那一行** | 报错就报在那里 | 栈顶常常是「受害者」，真正的问题在几层之前的错误数据 |
| **最后改的那行代码** | 时间上最可疑 | 可能只是碰巧；用 `git stash` 撤掉验证一次 |
| **最近合并的 PR** | 变更引入 bug 是常态 | 用 bisect 确认，别用直觉 |
| **「这里没判空」** | 看起来像标准答案 | 先证明这条路径上真的可能为 `None`，否则加了也没用 |

判据：**能用一个实验证伪的根因才是根因。** 说不清怎么验证的，都还是假设。

## 改测试的禁令

修 bug 的过程中，测试只允许改**搭建方式**（fixture、mock、数据准备），**不允许改期望值**。

| 允许 | 禁止 |
| --- | --- |
| 加 fixture、补 seed 数据 | 把 `assert status == 200` 改成 `== 500` |
| 修正 mock 的路径 | 加 `pytest.mark.skip` |
| 把断言拆细以定位问题 | 删掉失败的断言 |
| 改测试文件名/位置 | 把断言换成 `assert result is not None` 这种弱断言 |

如果修完之后必须改期望值才能绿——那不是修好了，是你改变了行为。**在汇报里单独写一行说明。**

## 汇报格式

```
根因：app/services/order_service.py:134 在 for 循环里逐条 commit，
      第 3 条失败时前 2 条已经提交，无法回滚。

证据：
  测试 test_batch_create_rolls_back_on_partial_failure
  - 修复前：FAILED  assert 2 == 0  （数据库残留 2 条订单）
  - 修复后：PASSED
  全量：412 passed（修复前 411 passed + 1 failed）

改法：循环内只 add，循环外单次 commit，except 里 rollback。
```

三件事缺一不可：**根因的一句话因果链**、**红→绿的同一个测试名**、**全量测试的对比数字**。

## 反模式

- **先改代码再补测试**。补出来的测试会不自觉地迁就改后的行为，永远绿。
- **测试里断言内部调用**（`mock.assert_called_once_with`）当成复现。这只证明了调用发生，没证明用户看到的症状。
- **修完顺手把测试删了**，理由「这个 bug 不会再有了」。它当然会回来，而且是以另一种形状。
- **根因写成「因为没做校验」**。这是「缺了什么」，不是「为什么出错」。要写清数据从哪来、到哪一步变成非法值、为什么没人拦住。
