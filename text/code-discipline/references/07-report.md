# 模式 7 — 单文件 HTML 报告

**不要输出 Markdown。** 不是讨厌 Markdown，是 Markdown 撑不住这类内容：一个审查报告里有结论、有分类、有证据链、有代码片段、有严重度分级，全塞进聊天会变成一条没人读完的长消息。

HTML 报告解决三件事：**分标签页**（一次只看一类）、**流程图**（把因果链画出来，而不是写成三段话）、**颜色**（严重度一眼可辨）。

## 硬约束

| 约束 | 为什么 |
| --- | --- |
| 单文件 | 发微信、丢群里、存归档，双击就能开。不能有相对路径依赖 |
| CSS / JS 全内联，无 CDN | 断网、内网、离线机器都要能看 |
| 无外部图片、无字体文件 | 同上。图标用 CSS 字符或 Unicode 画 |
| 生成后**直接打开浏览器** | 不开等于没交付。`--open` 一行搞定 |
| 聊天里只留 3–5 行摘要 + 文件路径 | 报告在文件里，结论在聊天里 |

## 工作流

```
1. 按模式 1–6 得到结论（这才是主要工作，别把时间花在排版上）
2. 把结论写成一份 JSON（schema 见下）
3. python scripts/build_report.py --spec report.json --out out/report.html --open
4. 在聊天里回 3–5 行：结论、最严重的一条、文件路径
```

**先有结论，再排版。** 反过来会变成「为了填满标签页而凑内容」。

## JSON schema

### 顶层

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `title` | ✅ | 报告标题。带上是哪次提交/哪个模块 |
| `subtitle` | | 一行元信息：commit、文件数、作者、时间 |
| `eyebrow` | | 标题上方的小字，默认 `CODE DISCIPLINE REPORT` |
| `verdict` | | `block` / `warn` / `pass`，决定顶部徽章的文字与颜色 |
| `summary` | | 一段话结论。**这是唯一会被认真读完的部分**，把最重的判断放这里 |
| `metrics` | | 顶部数字卡片：`[{label, value, tone}]` |
| `tabs` | ✅ | 标签页数组，至少一个 |
| `footer` / `generated` | | 页脚左右两段文字（范围说明、生成时间） |

### 标签页

```json
{ "id": "security", "label": "安全", "count": "1", "blocks": [ ... ] }
```

`id` 用于 URL 锚点（`#security` 可直接打开对应页），`count` 显示在标签后面的小数字。

### 区块（blocks）

八种类型。`tone` 在不指定时默认 `info`。

#### `heading` — 分节标题

```json
{ "type": "heading", "text": "攻击面遍历" }
```

#### `text` — 一段话

```json
{ "type": "text", "text": "以下项目按顺序过了一遍，没有发现问题。" }
```

#### `callout` — 一条判断

```json
{ "type": "callout", "tone": "bad", "title": "合入结论：拒绝",
  "text": "第 1 条是外部可直接触发的越权读取，必须先修。" }
```

用在：总结论、重要提醒、免责说明。**一个标签页里最多 2 个**，多了就没有重点了。

#### `cards` — 问题清单（最常用）

```json
{ "type": "cards", "items": [
  { "tone": "bad", "title": "批量查询把用户输入拼进 SQL",
    "file": "app/api/orders.py:88",
    "trigger": "GET /orders/batch?ids=1) UNION SELECT ...",
    "body": "ids 只做了 split，随后 f-string 拼进 IN 子句……",
    "fix": "改成 ANY(%s)，ids 先 int 校验并限长 100" }
]}
```

`file` 和 `trigger` 渲染成元信息行，`body` 是解释，`fix` 是带虚线框的修法。这四段对应模式 6 要求的四个字段——**卡片的结构就是审查格式本身**。

#### `flow` — 流程图

```json
{ "type": "flow", "nodes": [
  { "title": "GET /orders/batch", "note": "?ids=1,2,3", "tone": "info" },
  { "title": "ids.split() 直接拼字符串", "note": "orders.py:88", "tone": "warn", "via": "无类型校验" },
  { "title": "UNION SELECT 读出 users 表", "tone": "bad", "via": "任意 SQL 片段" }
]}
```

- 纵向链条，节点间有虚线和箭头。
- `via` 是**连线上**的标签，写「这一步什么变了」。这是整张图信息量最大的地方。
- 至少 2 个节点。超过 7 个就该拆成两张图。

**什么时候用流程图**：

| 场景 | 为什么适合 |
| --- | --- |
| 根因链 | 「输入 → 未校验 → 拼 SQL → 泄露」，一条线说清因果，比三段话快 |
| 请求经过的层 | 从路由到 DB，指出哪一层漏了校验 |
| 状态机非法迁移 | `created → paid → refunded`，画出跳过的边 |
| 修复前后对比 | 两张图并列，或一张图标出被切断的那一步 |

**不要**用它画组织架构、目录树、时间线——那不是因果链。

#### `table` — 对照表

```json
{ "type": "table", "head": ["#", "文件:行", "类别", "触发条件", "处理"],
  "rows": [["1", "app/api/orders.py:88", "安全", "ids 含引号", "本 PR 必修"]] }
```

列数必须和 `head` 一致，否则直接报错。适合：问题总表、参数对照、检查项清单。

#### `code` — 代码片段

```json
{ "type": "code", "caption": "app/api/orders.py:84-92（当前）", "text": "raw = ..." }
```

只放**必要的几行**，用来指认问题位置。整文件贴进去没人看。

#### `list` — 要点

```json
{ "type": "list", "ordered": false, "items": ["认证与授权：……", "输入边界：……"] }
```

适合「已检查项」这种并列清单。

## 颜色语义

固定映射，不要临时改。读者看第二份报告时应该能直接迁移。

| tone | 语义 | 用在哪 |
| --- | --- | --- |
| `bad` | 阻断 / 安全 | 漏洞、数据错误、必修项 |
| `warn` | 逻辑 / 正确性 | 事务边界、精度、off-by-one |
| `note` | 性能 / 资源 | N+1、索引、无界增长 |
| `ok` | 通过 | 确认不是问题的项、已修复 |
| `info` | 背景 / 说明 | 流程起点、范围声明 |

**同一个 tone 不要在一个标签页里表示两种意思。** `bad` 如果既表示安全漏洞又表示「重要提醒」，读者就学不会这套颜色。

## 标签页怎么分

默认三到五个，按**读者的问题**分，不按你的工作步骤分：

| 场景 | 推荐结构 |
| --- | --- |
| 提交审查 | 结论 / 安全 / 逻辑 / 性能 / 已检查 |
| Bug 复盘 | 症状 / 根因链 / 修复 / 回归测试 |
| 重构前评估 | 现状 / 行为清单 / 风险点 / 计划 |
| 对抗测试 | 总览 / 真问题 / 已知限制 / 覆盖矩阵 |

「已检查」那一页很重要——它证明范围，也防止别人以为你漏查了。

## 排错

脚本对 spec 是**严格校验**的，报错就是报错，不会静默丢内容：

| 报错 | 原因 |
| --- | --- |
| `缺少必填字段 'title'` | 字段名拼错，或值是空字符串 |
| `tone='danger' 不合法` | 只有 `bad/warn/note/ok/info` |
| `rows[2] 有 4 列，表头是 5 列` | 表格列数不对 |
| `tabs[0].blocks 至少需要一个 block` | 空标签页 |
| `spec 不是合法 JSON` | 中文引号、多余逗号、尾随逗号 |

先 `--check` 只校验不生成，改到通过再出文件。

## 反模式

- **报告比代码长**。20 行改动配 8 个标签页，说明重点没找对。
- **用 HTML 排版代替思考**。标签页不是为了好看，是为了「一次只看一类」。
- **把整段日志贴进去**。要贴就贴那 3 行关键的，前后各留 1 行上下文。
- **结论藏在第三页**。`summary` 里必须有最终判断，前三屏之内能看到「能不能合入」。
- **生成完不打开**。用户要的是看到，不是一个路径。
