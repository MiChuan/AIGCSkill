# 模式 2 — 最小改动

最小改动不是「写少点」，是**每一行都能被追溯到一条需求**。

## 改动预算

动手前先写下预算，写不出预算说明还没想清：

```
预计改动：3 个文件 / 约 40 行
- app/services/order.py   改 20 行（加事务）
- tests/test_order.py     加 15 行（2 个用例）
- app/api/order.py        改 5 行（错误码）
不碰：order_repo.py、models.py、迁移
```

超出预算是**停下来解释**的信号，不是「顺手多做点」。真实情况经常是超预算的（发现必须加一个参数穿过三层），那就明说：多改了哪一层、为什么绕不过去。

## 三张单子

### 禁止（这条需求没要求，就不写）

| 禁令 | 换成什么 |
| --- | --- |
| 新抽象层（interface / base class / 工厂） | 直接写函数，等第三处重复再抽 |
| 新配置项 / 环境变量 / feature flag | 硬编码当前值，需要时再说 |
| 新依赖 | 用标准库或已有依赖，实在不行先问 |
| 新的公共工具函数（`utils/` 里加一个） | 就地实现，或复用已有的 |
| 防御性检查（对内部函数入参判 `None`） | 信任调用方，见下面的判据 |
| `try/except` 兜底 | 让异常往上走，或只在边界处理 |
| 顺手重命名 / 顺手格式化 / 顺手调 import 顺序 | 单独开 PR，别混进来 |
| 顺手重构相邻代码 | 记下来，回头单独做（走模式 4） |
| 新增文档 / 注释块 | 只在「为什么」不明显的地方写一行 |

### 允许（这些不算超预算）

- 为验证改动而写的测试（模式 3、4、5 要求的一律算）
- 类型标注：改动的函数本来就有标注的，新代码跟着标
- 一行注释解释**为什么**（不是解释代码在干什么）
- 修正被改动代码里**直接相邻**的明显错误（比如那个函数里已经存在的 `== None`），但要单独列出来说明

### 灰区（可以加，但要在汇报里点名）

- 为了通过 lint 而不得不改的行
- 因为改了签名而被迫同步修改的调用方（这是真·必要，但要数清改了几处）

## 判据：什么算「实际不会发生的错误」

「不处理实际不会发生的错误」最容易被误用成「什么检查都不写」。用这三问过一遍：

1. **前提条件有真实来源吗？**
   `parse_config()` 的入参来自 `yaml.safe_load`，永远是 `dict`——加 `if not isinstance(cfg, dict)` 是废码。
   同一个人参如果来自 HTTP body，就必须校验。**看来源，不看函数。**

2. **这是边界还是内部？**
   用户输入、网络响应、文件内容、第三方 SDK 返回值 = 边界，必须处理。
   同一进程内、有类型标注、刚被自己构造出来的对象 = 内部，不用处理。

3. **处理之后，出问题是更容易发现还是更难发现？**
   ```python
   # 坏：出问题时静默返回空，日志里什么都没有
   try:
       total = calc(items)
   except Exception:
       total = 0
   ```
   兜底如果会**掩盖**故障，就不要兜。宁可让 500 响一次，也不要让用户看到错误的 0 元订单。

## 判据：什么算「为未来需求增加抽象」

三问：

1. **现在有几处调用？** 1 处 → 不抽。2 处 → 看第 2 问。3 处以上 → 抽。
2. **第二个使用者的需求已经明确了吗？** 没明确的第二使用者不存在，你现在抽的是**想象中的接口**。等它真的出现，它的需求大概率和你猜的不一样。
3. **抽象之后参数变多了吗？** 变多说明你在用参数弥补差异，这个抽象是错的。

```python
# 过度：为了「将来可能支持多种支付」加一层
class PaymentStrategy(ABC):
    @abstractmethod
    def pay(self, amount, ctx): ...

class AlipayStrategy(PaymentStrategy): ...
# 实际全项目只有一处调用，且只接支付宝

# 最小：
def pay_with_alipay(amount: Decimal, order_id: str) -> str: ...
```

## 读相邻文件：风格比对表

新代码必须和同目录同类文件**看起来像一个人写的**。逐项对：

| 维度 | 怎么对 |
| --- | --- |
| 命名 | 动词开头还是名词？缩写用不用？`get_` 还是 `fetch_`？ |
| 错误处理 | 抛自定义异常还是 `ValueError`？错误信息中文还是英文？ |
| 日志 | `logger.info` 还是 `logging.info`？带不带 `extra`？打不打 id？ |
| 返回值 | 返回 `None` 还是抛错？返回 dict 还是 dataclass？ |
| 异步 | `async def` 还是同步？有没有 `await` 漏掉的地方 |
| 注释 | 中文还是英文？写在函数头还是行尾？ |
| 测试 | 用 fixture 还是 `setUp`？断言库是原生还是 `pytest.raises`？ |
| 文件组织 | 一个文件一个类，还是一个模块一组函数？ |

对不上的时候**跟多数派**，不要跟「更正确的那个」。风格统一的价值高于你个人偏好。

## 案例：一次看起来最小、实际不小的改动

需求：订单列表接口要按 `created_at` 倒序。

```python
# 看起来最小
def list_orders(user_id, page=1, size=20):
    return db.query(Order).filter_by(user_id=user_id)\
             .order_by(Order.created_at.desc())\
             .offset((page-1)*size).limit(size).all()
```

问题藏在没写的那部分：

1. `created_at` 精度是秒，同一秒的多条订单顺序不确定 → 分页会重复/漏数据。**必须加第二排序键** `Order.id.desc()`。
2. 没索引的话，500 万行表上 `ORDER BY` 会全表排序 → 需要确认 `orders(user_id, created_at)` 索引存在。
3. 加了索引之后，原来的 `filter_by(user_id)` 执行计划会变 → 要看一眼 `EXPLAIN`。

真正的改动是 3 行代码 + 1 个索引确认。**最小改动不等于最短代码**，等于「满足需求所需的最少变更集」。上面三项都属于这条需求，不属于「顺手做的事」。

## 反模式

- **「反正都要改这个文件，顺便把命名统一一下」**。diff 从 20 行变 200 行，reviewer 找不到真正的改动了。
- **加一个 `if not x: return` 就以为处理了错误**。返回值是什么？调用方怎么区分「没数据」和「出错」？
- **为参数加默认值来兼容旧调用方**。默认值是隐形的第二套行为，除非调用方真的改不了，否则同步改调用方。
- **把测试写成 `assert True`** 来凑覆盖率。这不是测试。
