阻断 / 安全

批量查询把用户输入拼进 SQL

app/api/orders.py:88触发：GET /orders/batch?ids=1) UNION SELECT id,email,password_hash FROM users--

ids 从 query 取到后只做了 split(",")，没有任何白名单过滤，随后用 f-string 拼进 IN 子句。psycopg2 默认不允许一次执行多条语句，所以 DROP TABLE 那种写法会报错，但 UNION 注入成立：返回结构一致时结果会直接混进响应里。

修法改成按占位符展开：ids 先 int() 校验并限长（<= 100），再用 WHERE id = ANY(%s) 传 list 参数。校验失败直接 400，不要静默跳过非法元素。

app/api/orders.py:84-92（当前）
raw = request.query_params.get("ids", "")
ids = raw.split(",")
cur.execute(
    f"SELECT id, user_id, amount, status FROM orders WHERE id IN ({','.join(ids)})"
)
rows = cur.fetchall()
return {"items": rows}

已确认不是问题

同目录其他三个接口（orders.py:31 / :57 / :120）都用了参数化查询；认证中间件在路由之前挂载，这个接口本身需要登录态，所以是越权读取而不是未授权访问。

逻辑 / 正确性

循环里逐条 commit，失败时前几条已落库

app/services/order_service.py:134触发：一次提交 3 条，第 3 条因库存不足抛异常

for 循环体内每条 create 后立即 session.commit()。第 3 条失败时，前 2 条已经提交且无法回滚，接口返回 500，但数据库里留下了 2 条订单。前端重试会产生重复订单。

修法整个批量包在同一个事务里：循环内只 add，循环结束后一次性 commit；外层 except 里 rollback。重复提交问题另加幂等键（client_request_id + 唯一索引）。

逻辑 / 正确性

金额用 float 累加

app/services/order_service.py:151触发：price=19.99, qty=3 → 期望 59.97

total 是 float，19.99 * 3 = 59.970000000000006。写库时按 Decimal 转一次会截断成 59.97 没问题，但 downstream 的对账脚本读的是原始 float 字段，累计 1000 条后差 1 分以上。

修法全程 Decimal，入库前 quantize(Decimal("0.01"), ROUND_HALF_UP)；字段类型确认为 NUMERIC(12,2)。

逻辑 / 正确性

rollback 的异常被吞掉

app/services/order_service.py:170触发：数据库连接在 commit 阶段已断开，随后 rollback 抛 InterfaceError

except Exception: pass 包住 rollback。连接断裂时 session 处于不可用状态但被直接丢弃，连接池里留下脏连接，后续请求复用时会连续报错。

修法至少 except Exception as exc: logger.exception(...)，并且把 session 标记为需重建（session.invalidate()），不要吞。

性能 / 资源

列表页触发 N+1 查询

app/repo/order_repo.py:42触发：GET /orders?page_size=100 → 1 次主查询 + 100 次明细查询

返回订单列表后，序列化时逐条访问 order.items（惰性加载）。page_size=100 时 101 次往返，p99 从 40ms 涨到 780ms（本地 pg 实测）。

修法查询时加 selectinload(Order.items)，或在 repo 层批量取明细后按 order_id 组装。注意加了 selectinload 后不要再用 joinedload，否则会产生笛卡尔积。
