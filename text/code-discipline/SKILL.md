# 工程纪律：七个「先不要」

一句话：**这七条里有六条是「先不要 X」。它们不是拖延，是顺序。**

AI 写代码最典型的失败不是写错，是**写太快**：还没看懂就动手，动手就顺手重构，重构完发现原来那个 bug 还在，最后交一份漂亮但没有证据的总结。这七条是把「快」换成「准」的七个闸门。

## 每条在拦什么

| # | 纪律 | 拦的是这个本能 | 拿掉之后会怎样 |
| --- | --- | --- | --- |
| 1 | 先读懂再动手 | 看到需求就想写代码 | 方案建立在猜测上，改了三轮才发现方向错 |
| 2 | 最小改动 | 顺手抽象、顺手防御、顺手重构 | diff 里一半的改动没人要求，回归风险翻倍 |
| 3 | 先复现再修 | 看代码猜根因，改一行说「好了」 | 修的是症状，原 bug 还在，或者根本不存在 |
| 4 | 先固化再重构 | 边重构边改行为 | 重构后没人能证明「行为没变」 |
| 5 | 对抗性测试 | 只测 happy path | 上线后边界输入一碰就崩 |
| 6 | 只查三类 | 把审查变成风格警察 | 真正的注入和 N+1 沉在命名讨论底下 |
| 7 | 输出 HTML | 甩一大坨 Markdown 表格 | 重点被淹没，没人看完 |

## 七个模式

每一条都是一个可独立进入的模式。判定顺序按用户的话走，不要自作主张合并。

| 模式 | 用户这么说 | 硬门（不过不许往下走） | 产出 |
| --- | --- | --- | --- |
| **1 看清** | 「先别改，看看项目怎么实现的」「复述一下需求」 | 能说出测试怎么跑、改动点上下游各是谁；问题清单只剩「代码库查不到且影响方案」的 | 复述 + 假设 + 最小方案 + ≤3 个问题 |
| **2 减小** | 「最小改动」「别加抽象」 | 每一行 diff 都能对上一条需求 | 改动本身 + 一句话影响面 |
| **3 复现** | 「先别修」「先复现」 | 有一个**在未修改代码上失败**的测试，失败信息指向症状 | 红→绿 的同一个测试 + 根因一句话 |
| **4 固化** | 「先别重构」「先补测试」 | 新测试在**原代码**上全绿 | 行为固定的测试集 + 奇怪行为清单 |
| **5 攻击** | 「对抗性测试」「找找边界问题」 | 八类攻击面逐类过过，不是只测空输入 | 问题清单（已修 / 已知限制 / 不修）+ 回归测试 |
| **6 审查** | 「审查最后一次提交」「看看有没有问题」 | 每条都带 `文件:行` 和触发条件；风格问题一条不提 | 安全 / 性能 / 逻辑三张单子 |
| **7 交付** | 「不要 Markdown」「做成 HTML」 | 单文件、无外链、生成后已打开浏览器 | 一个 `.html` |

**模式会串联**，不是七选一。修 bug 的真实路径是 `1 → 3 → 2 → 5 → 7`；重构是 `1 → 4 → 2 → 5 → 7`；审查是 `6 → 7`。

## 七条通用约束

这七条比上面七个模式更底层，任何模式都不许破：

1. **每条结论都要能指到证据**——`file:line`、命令输出、测试名。说不出出处的判断一律标为「猜测」并明说。
2. **不问能读出来的问题**。见 `references/01-survey.md` 的提问过滤器：只有「代码库里查不到」+「答案会改变方案」+「不是偏好问题」三条同时成立才开口。
3. **改任何文件前，先读同目录里 2–3 个同类文件**，抄它们的命名、错误处理、日志、测试组织方式。风格不一致的改动等于给下一个人挖坑。
4. **不许为了通过而改期望**。测试可以改搭建方式，不能改断言值。改了就写进汇报。
5. **不确定就说不确定**，不要用「应该没问题」「理论上可以」糊过去。
6. **报告里不出现「建议考虑」「或许可以」**。要么是问题（给触发条件），要么不是（不提）。
7. **交付用模式 7**。任何超过一屏的结论都走 HTML，聊天里只留三五行摘要。

## 什么时候不吃这套

这套流程有成本，别用在不需要的地方：

- 纯文案、注释、格式、依赖版本号的小改
- 用户显式豁免：「这次直接改，不用复述」
- 明确的一次性脚本、临时代码

**安全相关的改动没有豁免权。** 用户说「快点改」，也至少要走完模式 3（先让测试红一次）——那通常是五分钟的事。

## 两个脚本

```bash
# 模式 1：省掉半小时翻目录
python scripts/survey.py                       # 扫当前目录
python scripts/survey.py --root ../myproj --json out/survey.json

# 模式 7：结构化结果 → 单文件 HTML，并直接打开
python scripts/build_report.py --spec examples/review-demo.json --out out/review.html --open
python scripts/build_report.py --spec examples/review-demo.json --check   # 只校验不生成
```

`build_report.py` 的 spec 是严格校验的：未知的 block 类型、列数对不上的表格、乱写的 tone 都会直接报错退出（退出码 2），不会静默丢内容——报告少了一段比报告报错更危险。

改脚本之后跑一遍：

```bash
python tests/test_scripts.py      # 8 tests，8 passed
```
